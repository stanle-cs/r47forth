Custom package v0.3 is up. It's the same idea as before, you build the
C47/R47 firmware with your own changes layered on top and nothing under
src/ gets touched, but I ended up rewriting most of the internals this
round so I'll walk through what changed.

[b]What changed from v0.2[/b]

[list]
[*]Overrides are git diffs now. v0.2 shipped whole edited files, and
there was no way to see what a package changed without diffing by hand.
Now I just open a file in patches/ and read it.
[*]A package is a flat directory that mirrors upstream paths, and the
tooling works out the rest. You drop new files in, pull upstream ones
with materialize, run a refresh, and the patches come out on the other
side.
[*]When two packages patch the same upstream file, the patches stack in
filename order (the NNN prefix), each on top of the previous result.
They can even land in different parts of one function. But if they hit
the same lines, configure fails and names the patch that collided.
[*]There's one entry point for the whole workflow now: ./package. Every
command below goes through it.
[/list]

[b]Making a package[/b]

Start a flat directory under packages/ and put your files where they'd
live upstream:

[code]
packages/my-pkg/
    keyboard.c      your edited copy of an existing upstream file
    my_module.c     a new source with no upstream counterpart
[/code]

For editing an upstream file, use materialize instead of copying it
out of your checked-out tree. If you just copy the file, there's a
chance your tree is on a different version than the package base, and
then the patch picks up upstream's changes as if they were yours:

[code]
./package materialize my-pkg keyboard.c
[/code]

This pulls the file as it was at the package's recorded base commit,
so when you edit it, the diff is just your changes. Refresh always
diffs against the base version either way, so if your tree happens to
be sitting exactly at the base, a straight copy works out the same.
Then:

[code]
./package refresh my-pkg
[/code]

sorts your files: paths that exist under src/c47/ become patches
against upstream, anything else gets copied in whole as a new source.
The raw tools under tools/ are still there and ./package just wraps
them, so scripts can call them directly.

[b]Building and testing with your package[/b]

[code]
make sim CUSTOM_PKG=packages/my-pkg
make dist_dmcp5r47 CUSTOM_PKG=packages/my-pkg
[/code]

The firmware test suite runs with your package active too, so you can
check you didn't break the calculator before flashing it:

[code]
make test CUSTOM_PKG=packages/my-pkg
[/code]

And make pkg_build PKG=packages/my-pkg does the whole release lap in
one go: cleans, runs the suite with the package active, refreshes, and
zips. If the tests fail, you get no zip. The zip also can't go over
PKG_MAX_SIZE, 1 MB by default.

[b]How patches compose[/b]

The resolver copies the clean upstream file in once, then applies each
package's patch in order with git apply -3. Order is the numeric
filename prefix, and ties go by position in your CUSTOM_PKG list. So
with

[code]
make sim CUSTOM_PKG=packages/alpha,packages/beta

packages/alpha/patches/005-keyboard.c.patch
packages/beta/patches/010-keyboard.c.patch
packages/alpha/patches/010-keyboard.c.patch
[/code]

keyboard.c gets alpha's 005 first, then the two 010s, alpha before beta
because that's their order in CUSTOM_PKG. After every patch the
resolver scans for conflict markers, even when git said the apply went
fine. Configure refuses a patch whose filename disagrees with its own
+++ header, and a patch whose target doesn't exist. And if two packages
try to provide the same new file, that's caught before the shadow tree
is built.

[b]Refresh before you build[/b]

The build reads only the generated patches/ and files/ directories,
never your flat working area. If you edit a source and forget to
refresh, the build still succeeds, it just compiles the code from
before your edit. I run ./package refresh at the top of my build
script.

Everything in a package directory is tracked in git, the generated
output included, since that's what the build actually reads. A manifest
of hashes backs this: hand-edit a generated patch instead of the
working copy and the next refresh warns you, then overwrites it.

[b]Where to get it[/b]

Target is R47/C47 on the DM42n (DMCP5 hardware). Licence is
GPL-3.0-only, inherited from c43; the full text ships in COPYING inside
the zip and on the release branch. I generated everything against
upstream c43 at commit 26ec91634. A newer upstream will probably work
too. The resolver checks every target before it applies anything, and
if a file moved, configure stops and tells you which one.

Download:
[url=https://github.com/stanle-cs/r47forth/tree/release/forth-core-stage2]release branch[/url]
with the zip beside it. Run the four test_pkg_patch tests from the
extracted zip before anything else, they check the tooling and don't
need an upstream tree.

The real example is my Forth package for the R47, which runs on this:
16 patches against upstream files plus 19 new sources. But that one
gets its own post.
