Custom package v0.3 is up. Same idea as before: build C47/R47 firmware with
your own changes layered on top, and never touch a file under src/. This
round the internals changed enough that I'll walk through them.

[b]What changed from v0.2[/b]

[list]
[*]Overrides are git diffs now. v0.2 shipped whole edited files, and you
couldn't tell what a package changed without diffing by hand. Open any
file in patches/ and the delta is just there.
[*]Two packages can patch the same upstream file. Patches stack in filename
order (the NNN prefix), and each one applies on top of the previous result.
[*]Different parts of one function compose fine. If two patches hit the same
lines, configure fails loudly and names the patch that collided. Nothing is
silently replaced.
[*]A package declares nothing. There's no meson.build and no file list to
keep up. It's a flat directory that mirrors upstream paths.
[*]The refresh tool sorts your files for you. Paths that exist under
src/c47/ become patches against upstream; anything else is copied in
whole as a new source.
[/list]

[b]Tooling[/b]

[list]
[*]--materialize pulls an upstream file into your working area when you want
to start editing it.
[*]The package records the upstream commit it was generated against, so the
patches always have a known base.
[*]--rebase-base moves a package forward to a newer upstream. Conflicts land
in your working copies as ordinary conflict markers and you resolve them
there.
[*]Content hashes in a per-package manifest catch drift. If you hand-edit
a generated patch instead of the working copy, refresh warns you and
overwrites it.
[*]A .pkgignore file keeps docs and dev scripts out of the generated output.
[/list]

There's also a small ./package entry point that wraps the common commands,
so the tool paths stop mattering.

[b]How composition works[/b]

The resolver materializes the upstream file once, then applies each
package's patch in order with git apply -3. Order is the numeric filename
prefix; ties go by position in your CUSTOM_PKG list. After every
application it scans for conflict markers no matter what the exit status
said. A patch whose filename disagrees with its own +++ header is refused,
and so is a patch whose target doesn't exist. Configure also catches two
packages providing the same new file, before any shadow tree gets built.

[b]pkg_build[/b]

make pkg_build PKG=packages/my-pkg cleans, runs the test suite with the
package active, refreshes, and zips the package. A failing suite produces
no artifact. There's a size gate too, PKG_MAX_SIZE, 1 MB by default.

[b]Refresh before you build[/b]

The build reads only the generated patches/ and files/ directories, never
your flat working area. Edit a source, skip the refresh, and what you get
is a clean build of your old code. Run the refresh first in your build
script and the problem goes away.

Everything in a package directory is tracked in git, working area
included. The generated output is the build input, and it's tracked with
everything else.

[b]Where to get it[/b]

Target is R47/C47 on the DM42n (DMCP5 hardware). Licence is GPL-3.0-only,
inherited from c43; the full text ships in COPYING inside the zip and on
the release branch. Generated against upstream c43 commit 26ec91634.

Download:
[url=https://github.com/stanle-cs/r47forth/tree/release/forth-core-stage2]release branch[/url]
with the zip beside it. Run the four test_pkg_patch tests from the
extracted zip before anything else; they check the tooling with no
upstream tree needed.

For a worked example, my Forth package for the R47 runs on this: 16
patches against upstream files plus 19 new sources. That one gets its own
post.
