# C47 benchmark suite

A reproducible performance-measurement apparatus for C47, aimed at the
question "how fast is this on the calculator?" while iterating on a PC.
The same nine programs run on real hardware (self-timed with TICKS) and in
an optimized headless simulator build (timed at microsecond resolution),
and a one-time hardware calibration lets local runs predict hardware
seconds per benchmark.

## Quick start (local)

```
make benchbin      # one-time: optimized headless build -> ./t47bench
make bench         # run the suite, print the report, write bench-results.csv
```

`make bench` runs `tools/bench/benchreport.py`, which drives
`res/SCRIPTS/bench.t47` inside `./t47bench --headless --snapskiprefresh
--reset`. Each benchmark gets one discarded warm-up plus five timed
repetitions (override with `--reps`); the report shows the median, the
spread (flagged above 10 %), iterations/second, and — once calibrated —
predicted DM42n seconds.

## The benchmarks

Every program is generated by `tools/bench/genbench.py` (regenerate after
editing; `--check` verifies the checked-in files match) and follows the
same shape: a TICKS bracket around a counted `DSZ`/`GTO` loop, elapsed
ticks (0.1 s units) left in X and stored in R97. The iteration counts are
fixed inside the programs and must never change without re-calibrating.

| program | axis |
|---|---|
| BMGTO | interpreter dispatch + local-label GTO scan (+ the per-step key poll that only hardware pays) |
| BMREG | numbered-register STO/RCL (direct-indexed control case) |
| BMVAR | named user-variable STO/RCL — the linear lookup of issue #555, with 10 decoy variables |
| BMRSV | reserved-variable STO/RCL (FV) — the gperf-hashed fast path |
| BMARITH | decNumber basics: + × ÷ √ |
| BMTRIG | decNumber transcendentals: sin, ln, exp |
| BMNQN | macro benchmark: 5 × NQueens(8) via the stock NQueens program (label NQ — load `res/PROGRAMS/NQueens.p47` first) |
| BMDISP | display-path op cost (PIXEL); measured locally but never hardware-predicted, because the simulator's GTK redraw does not model the hardware's DMA LCD writes |

`BENCHALL.p47` (label `BENCH`) is the one-shot hardware driver: it XEQs
each benchmark and copies its result to R80..R87. It stops early if any
benchmark program is missing, so load *all* the files first.

Harness register convention: R99 counter, R98 start ticks, R97 elapsed
ticks, R96 loop canary, R80–R87 driver results, R10–R14 operands. The
suite also allocates named variables (VV plus ten decoys and FV's value)
— run it on a state you don't mind touching, or save/restore state
around it.

Derived diagnostics worth knowing: `(BMVAR − BMREG) / (BMRSV − BMREG)`
isolates the name-lookup cost ratio between the linear user-variable scan
and the hashed reserved path (≈4.8× at the time of writing, matching the
measurements in upstream issue #555).

## Hardware run + calibration (DM42n)

1. Copy `res/PROGRAMS/bench/*.p47` and `res/PROGRAMS/NQueens.p47` to the
   calculator (USB disk mode).
2. READP NQueens.p47, then every `BM*.p47`, then `BENCHALL.p47`.
3. `XEQ BENCH` and wait (a few minutes; the display is mostly idle while
   the loops run).
4. Read R80..R87 — elapsed ticks (0.1 s) for BMGTO, BMREG, BMVAR, BMRSV,
   BMARITH, BMTRIG, BMNQN, BMDISP in that order.
5. On the PC, pair those readings with a fresh local run:

```
python3 tools/bench/benchreport.py \
    --calibrate "BMGTO=245,BMREG=180,BMVAR=520,BMRSV=210,BMARITH=310,BMTRIG=400,BMNQN=350" \
    --power "battery (80MHz)" --firmware "C47 3.x.y"
```

This writes `tools/bench/calibration-dm42n.json`; subsequent `make bench`
runs print predicted DM42n seconds. Calibration is per benchmark (not one
global factor) because hardware-only costs — the per-step keyboard poll,
flash wait states, LCD writes — scale differently with each instruction
mix; the spread of the factors is itself a profile of that "hardware
tax". Re-calibrate after firmware upgrades, on both battery (80 MHz) and
USB power (160 MHz) if you want both models.

## Honest limits

- Predictions are a calibrated model, not a cycle simulation: expect
  fidelity within a few percent for interpreter-bound workloads, worse
  wherever a change shifts the ratio of hardware-only costs.
- BMDISP is hardware-meaningful only; the local number is reported for
  regression tracking of the simulator path.
- Keyboard-to-display latency ("how snappy does it feel") is not
  measurable by this apparatus at all — it would need external
  instrumentation (camera or logic analyzer).
- Local numbers move with host load and thermals: run plugged in, machine
  otherwise idle; the report flags any benchmark whose spread exceeds
  10 %. The optimized build matters — the default debug simulator build
  measured 2.2–2.8× slower than `t47bench`, and unevenly so across
  benchmarks (BMGTO 2.2×, BMTRIG 2.8×), which distorts exactly the ratios
  this suite exists to measure; always use `make benchbin`.
