## 3. C17 — read this before attempting it

Confirmed, reproduced by mutation, **and I tried to fix it and failed.**

**The defect.** Browse to FWRD through the CATALOG tree, so the *owner's*
FWRD frame is slot 0. Press FORTH: the open sees FWRD already current, so
it pushes nothing and records `homePushed = 0` — correctly meaning "slot 0
is not ours". Press f+XEQ: `forthConsoleShowSurface` takes the
`cur == -MNU_FORTH` branch and overwrites `softmenuStack[0].softmenuId`
with the ALPHA index, **without ever asking whether that frame is the
console's**. Then any line running `calcModeNormal()` (`XEQ 'CLSTK'`)
pops it, because that guard matches `-MNU_ALPHA`. EXIT, and the owner gets
the catalog level that was underneath.

Frame *count* is conserved, which is why the landed battery passes; frame
*identity* is not.

**The obvious fix is not sufficient.** Gating the retarget on
`forthCapHomePushed()` and pushing when the console does not own slot 0
**failed the two probe rows it was meant to close and also regressed
`[open, alpha, ENTER, EXIT]`**, which had been passing — the owner's row
came back as a TAM menu (`-1387`). Reverted; the tree is green without it.

I did not get to the bottom of that interaction. What I would try next:

- The push-when-not-owned path sets `homePushed = true`, after which the
  *return* leg retargets rather than pops. Trace both legs together
  rather than the outbound one alone.
- `forthConsoleRestoreSurface` runs on the ENTER path and has its own
  push-and-take-ownership branch. Two functions can now both claim
  ownership of a frame in one line's lifetime.
- Sol's framing, reached independently and worth starting from:
  *"menu ownership — not merely visible menu identity — controls the EXIT
  ladder."* The right model may be an explicit owned-frame **identity**
  (which slot, which menu) rather than a single ownership bit.

The reproducing fixture is in the round-2 report under C17: the owner
fixture is `showSoftmenu(-MNU_CATALOG); showSoftmenu(-MNU_FORTH);` and the
differential is that a plain `1 2 +` line passes where a `XEQ 'CLSTK'`
line fails.

## 5. Things that downgrade work already done

**C22 — the C1 class test is weaker than the session suggested.** The
DMCP target build carries **no `-fstack-protector`**. The mutation that
went red for C1 went red because of the *simulator's* protector, not
because the canary test caught it. On the device — where C1's consequence
is a reboot — that backstop does not exist. The C1 *fix* is right; the
test is not the proof it appeared to be.

**Three vacuous tests in one session, all mine, all caught by running the
mutation and none by the gate.**

1. A hammer invariant comparing a `uint8_t` against 255 — `-Wtype-limits`
   caught it.
2. The C1 class test built its short integer with `255 XEQ 'HEX'` — `HEX`
   is a `CAT_FNCT` item reached by *bare name*, so the line raised
   label-not-found, X stayed a long integer, and the arm under test was
   never reached.
3. The C16 class test performed the save/restore *in the test body* and
   asserted the bits survived — testing its own copy of the block.

The rule that caught all three, and the one to keep: **a fixture must
assert it reached the state it claims to test**, and **a fix is not
finished until the mutation reddens.** A green suite proves nothing about
a test you just wrote.

## Two non-conformances, both now closed

**C-3, the render-time view clamp** (landed the same day, `d4a204d66`).
Upstream has this exact class — a display-window index that can outrun its
content — and solves it in two parts, neither of which is a write during a
paint: the WRITE clamp sits at the scroll site
(`scrollPemBackwards`/`Forwards`, manage.c:432-446), and the paint
TOLERATES an out-of-range window (`defineFirstDisplayedStep`,
nextStep.c:548-560, which breaks when content runs out). C-3 normalised the

`_forthConsoleViewBase`. The owner's ruling is unchanged — the band is full

view" rather than "where the last repaint left it". The class test asserts

write.

**C14, open since round 1 and never fixed.** `_forthConsoleEditorTop()`

defines.h:1518-1521). The fix the handoff had planned — two
`_Static_assert`s — was itself the workaround shape: assert that two copies
agree.

Now the numbers are COMPUTED from upstream's names by upstream's own
arithmetic: the short-line state takes the y its caller passes
(`Y_POSITION_OF_NIM_LINE - 3 - checkHPoffset`, screen.c:3886, because
showStringEdC47's wrapped-line reposition is guarded by
`lastline > yMultiLineEdOffset` and does not run), and the long-line state
takes the reposition's own `(yincr-1) + yMultiLineEdOffset * (yincr-1)`
(:1687). Both produce byte-identical values in the default layout — 128 and
67, 4 rows and 2 — so nothing repaints differently. The `_Static_assert`s
stay, but they now tie the band's row counts to UPSTREAM's names, so moving
a register line upstream breaks this build instead of silently painting the
transcript over the editor.

follow it, so the band would have overlapped the editor there. Reading
upstream's expression instead of copying its result makes the band track it
for free — which is the rule's whole argument in one line.
