# DECISION — Stage L host: PEM-pivot vs AIM plan of record

## 1. VERDICT

**Do not pivot. Stay on the AIM host.** The pivot's thesis is that hosting on `calcMode == CM_PEM` gives interactive Forth the record-instead-of-execute machinery for free. But the mode identity it adopts must be locally falsified in both of the two things the mode exists to do: to *show the stack* you must lie about `calcMode` (`src/c47/display.c:234-237` forces `DF_ALL`; `packages/forth-core/screen.c:3636` suppresses the X-line prefix), and to *run the line* you must lie about it again — because `fnGoto`'s first test is `if(tam.mode || calcMode != CM_PEM)` (`packages/forth-core/programming/lblGtoXeq.c:17`), so a Forth line that names a C47 label reaches `packages/forth-core/programming/lblGtoXeq.c:94-96` and **inserts a GTO step into FHIST instead of jumping**, then `runProgram` executes from `currentStep` inside the history program (`packages/forth-core/forth_compile.c:1408-1436` → `lblGtoXeq.c:200-210`). That is a confirmed finding, not a speculative one. Both lies are writable, but once both are written the pivot has bought nothing at run time and nothing at display time — it has bought only the input seam, which is one dispatch arm. Against that it adds a new screen renderer plus four implicit-output replications plus an unsized audit of ~148 live `CM_PEM`-conditioned sites, replacing a bounded, already-audited list of ~17 gate widenings. The display work is materially bigger than the dispatch work it replaces. Additionally the pivot commits every keystroke to program memory (`packages/forth-core/programming/manage.c:1104` delete + `:1113` re-insert) where the AIM host touches program memory once per ENTER — an arena cost that is binding under CLAUDE.md and currently unmeasured.

Two corrections to the plan of record are required regardless, and they are cheap (§5).

## 3. SHOWSTOPPERS

**One, and it is exactly the arbitrary-user-code case.**

`packages/forth-core/forth_compile.c:1436` calls `fnExecute((uint16_t)label)` unbracketed (the comment at `:1414-1434` states the `PGM_RUNNING` wrap is deliberately not applied). Interactively that takes `packages/forth-core/programming/lblGtoXeq.c:200-210` — `fnGoto(label); runProgram(false, INVALID_VARIABLE)`. `fnGoto` opens with `if(tam.mode || calcMode != CM_PEM) { …goto… }` (`lblGtoXeq.c:17`); under the pivot `tam.mode == 0` and `calcMode == CM_PEM`, so control falls to `lblGtoXeq.c:94-96` → `insertStepInProgram(ITM_GTO)` (`manage.c:1708`). A `GTO` step is written into FHIST under the cursor and `runProgram` then executes from `currentStep`, i.e. inside the history program. Calling a label is the most common thing a user does from a Forth line.

This is escapable — save `calcMode`, set `CM_NORMAL`, `forthOuterInterpret(aimBuffer)`, restore — but the escape has three properties that make it disqualifying rather than merely costly:

1. **It spans arbitrary, re-entrant user code**, not one bounded call. A line can `XEQ` a program containing `ITM_FORTH` steps; `runProgram` polls keys for abort (`lblGtoXeq.c:740-760`); error paths must restore. Contrast the plan of record's bracket, which wraps a single TAM dispatch.
2. **It concedes the thesis.** During the only moment the pivot's host mode would matter for execution, the host mode is switched off. The record-instead-of-execute semantics you adopted are precisely what you must suppress.
3. **`fnGoto` is one instance of a class you cannot enumerate cheaply.** The Forth inner interpreter reaches natives through `reallyRunFunction` (`packages/forth-core/forth_compile.c:1110`, `packages/forth-core/forth_inner.c:378`), bypassing the `runFunction` PEM divert — so the protection you *think* you inherit does not apply, and every leaf with its own `calcMode == CM_PEM` arm (≈148 sites, plus macro-hidden ones) is a live landmine reachable from user text.

A second-order consequence of the bracket: user code that runs a program calls `resizeProgramMemory`, which moves the whole region (`src/c47/memory.c:212-213`). Under the pivot `currentStep`/`firstDisplayedStep` point *into* FHIST at the open capture step for the entire run, so they must be re-derived as offsets afterwards (landed precedent: `forthCaptureSuspend` saves `(uint32_t)(currentStep - beginOfProgramMemory)` at `manage.c:1190-1191`, rebuilt at `manage.c:1210`,`:1236-1237`). Under the AIM host the line lives in `aimBuffer` and there is no in-program cursor to salvage.

Under the AIM host this showstopper does not exist: `calcMode == CM_AIM ≠ CM_PEM`, so `lblGtoXeq.c:17` takes the jump arm.

Everything else is expensive, not impossible.

## 4. IF PIVOTING (not recommended — minimum shape only, should the ruling be overridden)

- **Entry:** resolve FHIST's program number, then `goToPgmStep(fhist, 1)` followed by a second positioning call to reach the last step (`lblGtoXeq.c:155-158` → `:101-151`). Do **not** write `goToPgmStep(fhist, getNumberOfSteps())` — `getNumberOfSteps` (`manage.c:2374-2387`) reads the *global* `currentProgramNumber` and is evaluated before the call, so it counts the program you are leaving. Then `fnPem(NOPARAM)`; seed the line from X **after**, because the entry arm does `aimBuffer[0] = 0` at `manage.c:504`. Set `pemCursorIsZerothStep` explicitly for the empty-FHIST bootstrap (`manage.c:515-521` does not cover it).
- **Exit:** the EXIT teardown at `keyboard.c:3987-3993` is unreachable on the first press with a line open — the ladder consumes it at `keyboard.c:3926`, `:3935`, `:3941-3945` or `:3946-3976`. A single-press EXIT needs a new rung above `:3926`. Also guard the second exit at `keyboard.c:3169-3176` (`ITM_PR`) to call `forthCapClose()`.
- **ENTER:** run at `manage.c:1030`, between the `forthCheckSourceLine` gate (`:1025`) and `pemCloseAlphaInput` (`:1031`) — the only point where the line is live in `aimBuffer` and the gate has passed. Use `forthOuterInterpret(aimBuffer)` (`forth_compile.c:1591-1603`), **never** `forthProgramStep` (confirmed: different scope `forth_compile.c:1699-1717` + `forth_dict.c:493`, different lifetime `forth_compile.c:1702`, different mode `SKIP_DEFS` at `:687-711`). Bracket `calcMode = CM_NORMAL` around the call; save/restore `aimBuffer` (the interpreter can reach items that memset it: `src/c47/c47Extensions/addons.c:375`,`:451`,`:585`,`:667`,`:1016`); re-derive `currentStep`/`firstDisplayedStep` from offsets afterwards.
- **Display:** new sibling of `_refreshPemScreen` wired at `screen.c:6176`, `screen.c:6184`, `screen.c:2191`; it must still set `currentStep`, `programListEnd`, `lastProgramListEnd`, `tamOverPemYPos`; reuse `showStringEdC47` (`screen.c:1644`) for the line; bracket `calcMode` for the register draws (`display.c:234-237`) and guard the battery skip that bracketing arms (`screen.c:3246-3247`).
- **Suppressions:** `keyboard.c:3169-3176` (ITM_PR exit), `manage.c:2229-2258` (`insertUserItemInProgram` — add a `forthCapIsOpen()` early-out), `keyboard.c:3217-3226` (R/S in keys mode), `keyboard.c:3227-3230` (`.d` silently dropped on a non-empty line), plus a refusal rule for entering interactive Forth while a user PEM session is open.

## 5. NOT PIVOTING — what to adopt anyway

1. **Repair the fold bracket in STAGE_L_INTERACTIVE.md. The plan of record is wrong as written.** `forthCaptureSuspend` is called from `tamEnterMode` (`packages/forth-core/ui/tam.c:1180-1181`), which is reached from `packages/forth-core/items.c:744` under the gate at `items.c:736` — i.e. on the *key press that starts* the TAM session, one dispatch earlier than `tamProcessInput` (`ui/tam.c:1414`). Resume is in `leaveTamModeIfEnabled` (`ui/tam.c:1406-1408`), not at the tail of `_tamProcessInput` (which ends at `ui/tam.c:1146`). A bracket placed only around `_tamProcessInput` would **never reach the suspend**. Correct bracket: per-dispatch, at `items.c:736-744` (entry) *and* around `tamProcessInput` (`ui/tam.c:1414`) *and* covering `leaveTamModeIfEnabled` (`ui/tam.c:1363`) — restoring `CM_AIM` at the end of each dispatch so the between-keystroke render stays on the AIM arm. Step materialisation for the canonical numeric fold is `ui/tam.c:908` (not `:1103`, which is the alpha-buffer branch entered at `ui/tam.c:939`).
2. **Adopt the ENTER seam and the run call verbatim.** Same site (`manage.c:1030`) and same function (`forthOuterInterpret`) apply on the AIM host, and the confirmed scope/lifetime/mode asymmetry (`forth_compile.c:1591-1603` vs `:1726-1740`) rules out the "just run the FHIST step" shortcut on either host.
3. **Adopt FHIST recall as a text copy, not a step execution.** Payload is at `step + 4` for `step[3]` bytes and is **not** NUL-terminated (`_forthCapBuildStep` `manage.c:846-859`; `forthStepPayload` `packages/forth-core/forth_bridge.c:60-68`; extraction idiom `forth_compile.c:1669-1671`). One small new function; do not reuse the `+3` figure that appears in the investigation notes — it points at the length byte.
4. **Add the divert coverage the plan of record misses.** The new arm at `items.c:651` sits *above* `items.c:665-735`, so the dynamic-menu and USER-mode RCL/XEQ arms (`items.c:670`,`:699`,`:711`,`:719`, `keyboard.c:2259`,`:2283`, `screen.c:818`,`:836`, `forth_bridge.c:30`) are unhandled on the AIM host too. Either place the divert above them or add a `forthCapIsOpen()` early-out in `insertUserItemInProgram` (`manage.c:2229-2258`).
5. **Divert `fnKeyEnter`'s CM_AIM arm.** It pops softmenus, calls `calcModeNormal()`, and on a non-empty `aimBuffer` stores the buffer to X as a `dtString` with a lift (`packages/forth-core/keyboard.c:3513-3570`) — none of which a REPL ENTER wants. Add it to the plan as an explicit seam.
6. **Keep the `determineItem` fix** (`packages/forth-core/keyboard.c:1686`) and extend it to `ITM_RS` if R/S is to mean "run the line" rather than type `?` (`src/c47/assign.c:45`, `primaryAim == ITM_QUESTION_MARK`).
7. **Narrow the T5 claim in the doc.** "Zero new display code" is refuted. What actually survives: `_refreshNormalScreen`'s AIM arm paints T/Z/Y **only when `yMultiLineEdOffset == 3`** (`screen.c:5935`, set at `screen.c:1675` for short lines; `1` at `screen.c:1669`,`:1682` for long lines and checkHP), and the edit line occupies REGISTER_X because `AIM_REGISTER_LINE == REGISTER_X` (`packages/forth-core/defines.h:1495`). So the AIM host gives T/Z/Y + line for short lines and line-only for long lines, with X never visible while composing. That is still enough to justify L-R2, but the doc must say it in those terms and rule explicitly on the long-line case.
8. **File two bugs found in passing, independent of Stage L.**
   - `leavePem` use-after-free: `scanLabelsAndPrograms` frees `labelList`/`programList` (`manage.c:132-133`) and can early-return on RAM_FULL (`manage.c:155-159`,`:162-166`); `leavePem` then calls `defineCurrentStep` (`keyboard.c:2409`) which dereferences `programList[...]` (`src/c47/programming/nextStep.c:533`). Reachable once FHIST eviction runs at the L-R7 cap.
   - `.d` keystroke silently dropped: `keyboard.c:3227` is gated `aimBuffer[0] == 0`, so with text in the line no branch matches, `keyActionProcessed` stays false, and the key vanishes.
9. **Adopt the ITM_PR observation as a suppression on the AIM host too** if PRGM remains reachable from interactive Forth: `keyboard.c:3169-3176` never calls `forthCapClose()`.
