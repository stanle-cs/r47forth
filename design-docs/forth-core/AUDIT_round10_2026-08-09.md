### R10-1 — the shared cursor restore never restores `savedZerothStep`: the field is dead at both call sites, and the PEM zeroth-step position is lost on every console ENTER

`packages/forth-core/programming/forth_fold.c:624` — wrong-result, high
confidence, contracts dimension, reachability lens. **A behaviour
regression this wave introduced.**

**Reaching input.** (1) In PEM, park on a program at the ZEROTH step:
with the cursor on step 1, press BST once — `nextStep.c:322-326` sets
`currentLocalStepNumber = 1`, `pemCursorIsZerothStep = true`, and the
`0000:` line goes reverse-video (`manage.c:543`). (2) Leave PEM. Nothing
on the way out clears the flag: `leavePem()` (`keyboard.c:2519-2544`)
saves and restores `currentLocalStepNumber`/`currentProgramNumber` and
never touches it; `calcModeNormal()` does not either. (3) Press FORTH,
type `1 2 +`, press ENTER. `forthInteractiveEnter` →
`forthHistoryPush` → `_forthHistSaveCursor` records
(program, localStep = 1, zeroth = 1) → `_forthHistRestoreCursor` →
`_forthRestoreCursorTuple(program, 1, 0, 1)`. (4) At `:624`
`if(localStep > 1 && localStep <= getNumberOfSteps())` is **false** —
a zeroth-step cursor is always `localStep == 1` — so the else arm at
`:631-634` forces `zerothStep = 0` and `:637` writes
`pemCursorIsZerothStep = false`. (5) EXIT, press PRGM. With
`currentLocalStepNumber == 1`, `fnPem`'s normalisation takes **neither**
arm (`manage.c:528-534`), so the flag stays false.

The identical path exists on the fold side: `forthFoldEnter` (`:1144`)
saves `savedZerothStep` and forces the global false, `forthFoldLeave`
(`:1459`) restores through the same helper — so a console STO/RCL/DELP
TAM loses it too. The first ENTER of a session loses it twice, because
`forthHistoryEnsure` runs the same bracket while creating FHIST.

**What breaks.** The cursor comes back sitting **on** step 1 instead of
above it: the `0000:` reverse-video line is gone, and the next step the
owner keys in is inserted **after** step 1 instead of before it —
`addStepInProgram`'s pre-move (`packages/forth-core/programming/manage.c:2179`)
is gated on `!pemCursorIsZerothStep`, so with the flag cleared
`currentStep` advances first. A program step lands in the wrong place,
silently, with no error. Before this wave both sites assigned
`pemCursorIsZerothStep = savedZerothStep` unconditionally and the
position survived; `git diff 013256b76 9230d36b2 --
packages/forth-core/programming/forth_fold.c` shows both of those
assignments being removed.

**Violated.** `forthFoldEnter`'s own contract for the field it saves
(`forth_fold.c:1146-1156`): *"MUST: a parked capture step is a real step,
never the zeroth-step pseudo-position. … It is a persistent global with
no reset on leaving PEM."* The save exists solely so the leave can put it
back. And the helper's own justification for zeroing it (`:629-631`) —
*"The saved display window described a program state that no longer
exists, so it is not restored either"* — names an **invalidated** cursor,
while the branch it sits in also catches `localStep == 1`, which is
always valid. The same banner says so twelve lines up: *"Step 1 always
exists, so the first navigation is unconditionally safe."* The condition
`localStep > 1` conflates "the second navigation is redundant" with "the
saved tuple is invalid".

No ruling covers the change. DESIGN-HISTORY.md's R9-1/R9-2 entry
justifies the step-1 fallback only for a cursor the dispatch invalidated
and says nothing about a valid `localStep == 1`.

**Class.** Consolidation that makes an unconditional restore conditional
— a saved field whose restore is now gated by a predicate about a
*different* field of the same tuple. Sibling of R8-1/R9-1's
"saved cursor tuple with an unmaintained half", one turn further on: the
half that is now unmaintained is the one the consolidation was supposed
to carry.

**Class test.** Enumerate every field of both saved tuples (program,
localStep, firstDisplayed, zerothStep) and assert, per field, that a
save/restore round trip with **no** intervening list mutation is the
identity — the property the gate has no fixture for today. Then drive
each list mutation (delete-at, delete-before, evict) and assert only the
fields the ruling says may change do change. Red-first reproducer: the
sequence above.

**Why nothing caught it.** Every fixture in the tree sets
`pemCursorIsZerothStep = false` before driving. The wave's own zeroth-step
subcase, `[C6.8]` in `test_capture.part.h`, passes **only** because its
fixture parks on the END step (`tpSelectStep` → `currentLocalStepNumber
= 2`) while forcing `pemCursorIsZerothStep = true` — a (localStep 2,
zeroth true) pairing no real path produces, and the one pairing that
keeps the subcase on the arm where the flag *is* restored. Repointing
that fixture at step 1 — the pairing the real state always has — turns
the gate red on the subcase's own assertion:
`[8] FAIL: pemCursorIsZerothStep not restored to true after leave`.

### R10-2 — `forthConsoleHomeRow` lands only when exactly one frame is stacked over the console; at depth two the "land half" the ruling calls the point of the gesture does not happen

`packages/forth-core/forth_menu.c:702` — wrong-behaviour on a named
gesture, medium confidence, design dimension, correctness lens.
**Executed, not argued.**

**Reaching input.** Console open in keys mode, then stack two rows over
it — the state the design explicitly contemplates (*"rows the USER
stacked sit above the base (the EXIT ladder's overlay rung unwinds them
one press at a time)"*). Any two menu pushes do it: `items.c:743`'s
divert into the capture is gated on `func > 0` and its own comment states
that softmenu ids arrive **negative**, so every menu-opening softkey
dispatches natively and pushes a frame over the live console at any
depth. Now press HOME.3 (`keyboardTweak.c:196`, or the long-f seam at
`screen.c:925`). `forthCapInteractiveLive()` is true;
`forthConsoleBaseOnTop()` is false via its *"ours is buried"* arm;
`popSoftmenu()` removes **one** frame; `forthConsoleShowSurface()` then
finds slot 0 unowned, walks to the buried owned frame, retargets it **in
place** and returns without raising it. Final state: the second overlay
is still the displayed row.

Executed at the audited tip through the real long-f seam:

```
stacked2:         m0=MyAlpha m1=FIN m2=FORTH(owned) m3=STK  ownedSlot=2 live=1 keys=1
after HOME.3:     m0=FIN     m1=FORTH(owned) m2=STK          baseOnTop=0 keys=1
after 2nd HOME.3: m0=FORTH                                   baseOnTop=1
```

**What breaks.** The owner presses the go-home gesture and does not get a
home row: one overlay disappears and another is showing. It takes as many
presses as there are stacked rows. Worse, and unclaimed by the finder:
when the frame the pop reveals is MyAlpha in CM_AIM, upstream's
`popSoftmenu()` fires its own `changeToALPHA()` and a raw `-MNU_ALPHA`
row lands on top while `forthCapKeysMode()` is 1 — reproduced at depth 2:

```
after call: m0=ALPHA m1=MyAlpha m2=FORTH(owned)   baseOnTop=0 keys=1
```

That is the exact K-R3 state R9-4 was written to eliminate and that test
`[7]` now asserts against, reachable **through the fixed code**. A second
press does not clear it. Pre-R9-4 this state fell through to the native
arm, which always pushed a row — the wrong row in keys mode, which was
the bug, but it landed. The fix traded the landing guarantee for the row
correctness without saying so.

**Violated.** The R9-4 ruling's own statement of what it implements:
*"dismiss the alphabetic overlay if one is on top, then LAND on the row
that matches the current input context. Two halves, and the second is the
one the gesture is named for: openHOMEorMyM OPENS a home row"* — and
*"the faithful translation keeps both halves"*. Upstream's arm pops at
most one frame **and** unconditionally `showSoftmenu(-MNU_ALPHA)`, so it
lands at every depth; this translation lands only at depth 1.

**Class.** A two-half gesture translated with the second half made
conditional on a state the first half does not establish. Related
mechanism worth naming separately: `forthConsoleBaseOnTop` is reused here
past its stated scope — its comment defends its unregistered fallback as
*"the conservative fallback: it can only make rung 3 decline a pop, never
over-pop"*, a safety property stated for the EXIT consumer, which inverts
at a consumer that pops when the predicate says false.

**Class test.** Parameterise the HOME.3 drive over overlay depth 0, 1 and
2, and assert the **positive** property at each depth —
`forthConsoleBaseOnTop()` true and `currentMenu()` equal to the row the
sub-mode names — rather than the absence of one menu. Add the K-R3
conjunct at every depth: `forthCapKeysMode()` and `currentMenu()` never
disagree after the gesture returns. Both supporting artefacts share the
blind spot today: test `[7]` stacks exactly one frame, and the group-I
pin *"twin HOME.3 sites going through forthConsoleHomeRow()"* counts call
sites, not the invariant.

### R10-4 — check H's symbol scanner counts comment text as "the symbol is live", so it cannot fail for the case R9-8 built it for

## 7. Verdict

**Would I ship this? Not before R10-1.** It is a wrong result on the most
common gesture the stage has — every console ENTER — it was introduced by
this wave, it costs the owner a program step landing in the wrong place
with no error, and its fix is a condition, not a redesign. R10-2 is the
second door and it needs a ruling before code moves: HOME.3 with the
console buried under more than one row either unwinds to the console's
own row or pops one frame per press, and R9-4's own text says the gesture
is named for landing. Everything else is next-edit insurance or
instrument repair.

**Where it breaks first.** PEM → BST to the `0000:` line → EXIT → FORTH →
type anything → ENTER → EXIT → PRGM: the zeroth-step position is gone and
the next keyed step is inserted **after** step 1 instead of before it.
Second: console open in keys mode with two rows stacked → HOME.3 → no
home row, and if the revealed frame is MyAlpha in CM_AIM, a raw ALPHA row
over a keys-mode keypad — the K-R3 state the wave's own test asserts
against, reachable through the fixed code.

**What I would leave alone if the goal were correct code rather than an
audit-clean tree.** R10-8 (test `[10]`'s third conjunct — the sibling
subcase still reddens the shared bound, so the class is not uncovered,
only that member), R10-9 (the DESIGN.md `files/` list — wrong and worth
one command, but nothing depends on it at runtime), and R10-10 (a
one-token line number). R10-7 I would fix, because it is one line and the
mutation showed the subcase certifying "an evicting push" after a push
that evicted nothing. R10-6 I would fix even under the strict reading,
because runs 3 and 4 of its mutation matrix show the fixture stops
detecting the actual round-9 defect the moment an unrelated byte moves —
that is not tidiness, that is a net with a hole nobody will see open.
R10-3, R10-4 and R10-5 I would fix before round 11 accepts any new pin:
they are the audit's own instruments and two of them currently report a
success they have not earned.

**The pattern, tenth round running.** The findings are in the fixes
again, and this round says where inside the fixes: **five of ten are in
the machinery the wave built to stop the next round's findings.** Round 9
landed four correct behavioural fixes and three incomplete
generalisations, and every one of the incomplete generalisations is a
guard, a pin or a fixture. The firmware this wave touched is in better
shape than it was; the apparatus that is supposed to keep it that way is
in worse shape than it reports.
